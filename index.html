01 / ABOUT

Hi, I'm David.

XL

I'm a Senior Solutions Architect for Dynamo and Inference Infra at NVIDIA in Shanghai, and the subject-matter expert for NVIDIA Dynamo and Triton Inference Server in China. My days are spent inside large LLM inference clusters with the engineering teams of China's biggest internet companies: deciding where a request should run, what stays in KV cache, how prefill and decode are split across machines, and how fast a new worker can come up.

Lately most of that work is about agents rather than chatbots. Agent trajectories interleave generation with tool calls, their context only grows, and the metrics that matter shift from a single request's latency to the cost of a whole session. Making inference systems understand that shape is what I find most interesting right now, and most of it ships as open source in Dynamo and the engines around it: SGLang, vLLM and TensorRT-LLM.

Before NVIDIA I built perception and CNN pipelines for driver-assistance SoCs at Renesas in Detroit and the Bay Area, and LiDAR / camera localisation for autonomous driving prototypes. I studied electrical and computer engineering at Arizona State and Huazhong University of Science and Technology.

02 / FOCUS

Three problems I keep coming back to

One theme runs through all of them: placement, retention and restart decisions have to be made at the agent level, not the request level.

I

Where a request runs

KV-aware routing that weighs prefix cache reuse against live load, and decides whether prefill is worth disaggregating at all. Backed by Flash Indexer, a positional index fast enough to keep up with production request rates.

routingpd disaggflash indexer
II

What stays in KV cache

Program-aware scheduling that pauses and resumes whole agent trajectories at tool boundaries instead of evicting request by request, and multi-tier KV offload across GPU, CPU, disk and RDMA.

thunderagentflexkvsession aware
III

How fast a worker comes up

Cold start as a pipeline: streaming weights and compile artifacts from a running peer, or restoring a fully initialised process, so elastic inference on Kubernetes stops paying initialisation over and over.

model expresssnapshotkubernetes
03 / WORK

Selected work, 2025 – 2026

01agentic serving

Program-aware scheduling for agent trajectories

Ported and productionised ThunderAgent-style scheduling in Dynamo: pause and resume whole agent programs at tool boundaries instead of evicting request by request, with a native session-aware admission policy in the KV router. Large gains in prefix hit rate and TTFT on SWE-bench Lite workloads.

dynamo routersglangrust / python
02routing

KV-aware routing in production

Benchmarked Dynamo's KV-aware router against round-robin and session-sticky strategies on long-context multimodal traffic; showed that balancing cache reuse against live load beats maximising hit rate alone, cutting TTFT several-fold at equal QPS.

flash indexerpd disaggproduction a/b
03kv cache

Hierarchical KV cache offload

Contributor to FlexKV, a multi-tier KV cache system (GPU, CPU, disk, remote) integrated with TensorRT-LLM and NIXL; worked on CUDA IPC transfer paths and host-memory accounting for disaggregated deployments.

flexkvtensorrt-llmcuda ipc
04rl infrastructure

Dynamo as the rollout engine for verl

Integrated Dynamo into the verl reinforcement-learning stack so agentic rollouts run on a disaggregated, session-aware serving layer. Delivered as a recipe in verl-recipe together with the verl community.

verlrl rolloutmulti-turn agents
05performance

Automated parallelism sweeps for PD-disaggregated serving

Built a fully automatic sweep that explores TP / PP / DP-attention / EP / MTP configurations for prefill and decode under a given SLA, matches QPS between the two sides, and reports throughput per 1,000 GPUs on PCIe-only Blackwell workstation clusters.

sglangsla-drivenshell / python
06simulation

Digital twins for inference clusters

Validated Dynamo's simulation stack (AI Configurator and DynoSim) end to end against real GB200 runs for KV-router deployments, so deployment configs can be tuned before touching hardware.

ai configuratordynosimgb200
